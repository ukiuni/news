# JEP 534: Compact Object Headers by Default - コンパクトオブジェクトヘッダをデフォルトにする
Javaのメモリが小さく速くなる――HotSpotがオブジェクトヘッダを「小型化」してデフォルト化する理由と影響

## 要約
JEP 534はHotSpot JVMで64-bit環境におけるオブジェクトヘッダを既存の96–128ビットから64ビットに縮小し、これをデフォルト動作にする提案です。ヒープ削減、デプロイ密度向上、データ局所性の改善が期待されます。

## この記事を読むべき理由
クラウドやコンテナでのコスト削減、レイテンシ／スループット改善を狙うJavaエンジニアや運用担当者は、ヘッダサイズの変化がアプリのメモリ使用量やGC動作に直結するため、この変更を理解しておく必要があります。

## 詳細解説
- 背景と経緯  
  - コンパクトオブジェクトヘッダはまずJEP 450（JDK 24）で導入され、JEP 519（JDK 25）で製品機能化されました。JEP 534はそれをデフォルトにする提案です。既にOracle・Amazon・SAPなどで大規模なテスト・運用実績があります（AmazonはJDK 17/21向けにバックポート運用）。
- 何が変わるか（技術的ポイント）  
  - 64-bitアーキテクチャでオブジェクトヘッダを96–128ビット → 64ビットに縮小。これによりオブジェクト当たりのメモリが削減され、ヒープ総量が小さくなります。結果としてGC回数やCPU時間が減り、データ局所性が向上します。
- ベンチマーク事例（原報告の結果）  
  - SPECjbb2015でヒープ使用量が約22%減、CPU時間8%減、GC回数が約15%減（G1/Parallelいずれも）。並列JSONパーサーで約10%の実行時間短縮。実ワークロードでの効果が報告されています。
- 互換性とリスク  
  - 旧12バイトレイアウトを即座に削除するのは非目標。将来的にオブジェクトヘッダに追加ビットが必要になった場合は、Valhalla向けに4ビットを予約済みで、さらに必要ならProject Lilliputの手法で圧縮表現を調整する計画があります。JDK 25まではコマンドラインオプションで制御可能です。

## 実践ポイント
- 試す（ステージングで必須）  
  - JDK 25以降を使う場合、まずステージング環境でアプリを動かしてメモリ／GC挙動を測定する。既存のLTS（17/21）を使う場合はベンダーのバックポートやビルドを検討。
- フラグ操作（検証用）  
```bash
# 有効化（JDK24では必要だった）
java -XX:+UseCompactObjectHeaders -jar app.jar

# 無効化（デフォルト化後、オフにする場合）
java -XX:-UseCompactObjectHeaders -jar app.jar
```
- 測定すべき指標  
  - ヒープ使用量（jcmd/jmap）、GC回数・時間（GCログ/jstat）、スループット／レイテンシ、ネイティブライブラリやJNI周りの互換性。
- 注意点  
  - サードパーティのバイナリやヒープ解析ツールがヘッダフォーマットに依存している場合、ツール側の対応が必要になることがあります。運用環境では段階的なロールアウトと退避プランを用意してください。

まとめ：JEP 534はクラウドコスト削減やパフォーマンス改善に直結する有望な変更です。まずはテスト環境で影響を把握し、本番切り替えは段階的に行いましょう。
