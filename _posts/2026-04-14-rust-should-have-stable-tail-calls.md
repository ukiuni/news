# Rust should have stable tail calls - Rustは安定した末尾呼び出し（テールコール）を持つべき
Rustで「末尾呼び出し」を確実に使えるようにする試み — 高速な状態マシンや低レイヤ最適化に効く機能をめぐるロードマップ

## 要約
末尾呼び出し（tail call）は関数の最後の呼び出しで呼び出し元のスタックフレームを再利用でき、再帰を安全に使えたり、低レイヤ最適化（状態機など）で有利になる。Rustコミュニティはこれを安定化させるためのプロジェクトを進めており、まずは2026年に前提整備、2027年を見据えた安定化を目標にしている。

## この記事を読むべき理由
- Rustで高性能なインタプリタ・デコーダ・レキサーなどを作る人は、末尾呼び出しで実効的な速度改善とコード生成の制御が得られる可能性があるから。
- 現状はバックエンド（LLVMなど）やプラットフォーム対応の問題で未完成なので、Rustの将来機能や移植性に関心がある人に必読。

## 詳細解説
- 末尾呼び出しとは：関数が最後に別関数を呼んで即戻る場合、呼び出し元のスタックを再利用して呼び出せる最適化。再帰でスタックを増やさない、ループ代替などに使える。
- Rustの実装案：explicit tail calls（キーワード become）で「この呼び出しを必ず末尾呼び出しにしてほしい」と明示できる。例：
```rust
#![feature(explicit_tail_calls)]
fn foo(a: i32, b: i32) -> i32 { become bar(a, b) }
fn bar(a: i32, b: i32) -> i32 { a + b }
```
- 同一シグネチャ制限：tail callは呼び出し側と被呼び出し側でレジスタ保存や引数配置が一致している必要があり、Rustでは同じシグネチャを要求する（大量のフィールドはレジスタに乗らずスタックへ落ちる問題）。
- なぜ重要か（低レイヤでの利点）：
  - 状態マシン実装でジャンプテーブル＋末尾呼び出しの組合せは、分岐予測と局所最適化に有利で実測で数％の高速化を生むことがある。
  - 小さな関数に分けることでレジスタ使いを制御しやすく、不要なパスが最速経路のレジスタ割り当てを邪魔しにくい。
- 課題：LLVMなどのバックエンドがターゲットごとに末尾呼び出しを個別実装しており、サポートが不均一（wasm は専用機能が必要、PowerPCはTOC扱いで難しい等）。Rustは移植性を重視するため、部分的なサポートでは安定化できない。
- 代替／併走案：
  - Rust側で直接ジャンプ（computed goto 相当）を生成する手法（LLVM の indirectbr）を #[loop_match] 拡張で実装する案。ローカルジャンプなので移植性が高く、状態構造が大きい場合に有利なことがある。
- 進め方：まず extern "Rust" 向けに範囲を絞って対応、コンパイラ内で既知呼び出しを直接ジャンプに変換する最適化、並行して computed-goto 系のバックエンド拡張を進める。安定化にはさらなるLLVM改善と資金・貢献が必要。

## 実践ポイント
- 試す：feature gate（explicit_tail_calls）は実験的なので nightly で試す（上のコード参照）。
- ベンチ：状態マシンやインタプリタを実装して、末尾呼び出し版とループ版を実測比較する。分岐予測やレジスタ保持が効いているかをアセンブリで確認すると違いが分かる。
- 代替を検討：大きな状態構造がある実装では computed-goto（将来的な #[loop_match] の拡張）を待つか、手作業でジャンプテーブル風に書いてみる。
- 貢献・注目：プロジェクトは資金と開発者リソースを求めている。興味があるチームは支援やテスト、ターゲットでの検証に参加すると早期安定化に貢献できる。

短くまとめると、末尾呼び出しは一部の低レイヤ最適化で強力だが、移植性とバックエンド対応が課題。Rust側の段階的対応とLLVM改善で「使える機能」にするための動きが進んでいます。
