# What Game Engines Know About Data That Databases Forgot - ゲームエンジンが覚えていて、データベースが忘れたデータ設計
ゲームエンジン流の「メモリとアクセス優先」データ設計が、サーバー向けデータベースに与える示唆

## 要約
ゲームエンジンのEntity–Component–System（ECS）設計とデータベースのACID設計を融合したTyphonは、「キャッシュ局所性」「ゼロコピー」「コンポーネント単位のMVCC」「組込型インデックス／空間構造」などで、ゲームサーバーが求める高速性と安全性を両立する。

## この記事を読むべき理由
日本のオンラインゲーム／リアルタイムシミュレーション開発者やライブ運用エンジニアは、低レイテンシで大量エンティティを扱いつつ、課金や進行データの耐障害性も確保する必要がある――その設計指針が具体的に学べるため。

## 詳細解説
- 問題の本質  
  ECS（ゲーム側）と従来RDB（エンタープライズ側）は言葉が違うだけで似た構造を目指す。両者の発想を統合すると、性能重視のメモリレイアウトとトランザクション保証が同居できる。

- ゲームエンジンからの学び（Typhonが取り入れた要素）  
  1. キャッシュ局所性をデフォルトに：同種コンポーネントを型ごとに連続配置することで、L1ヒットは約$1\text{ns}$、DRAMミスは約$60\text{–}70\text{ns}$といった大きな差を避ける。  
  2. ゼロコピーアクセス：メモリ上が最終レイアウトであり、デシリアライズ不要。GCやヒープ割当を回避して超低レイテンシを達成。  
  3. エンティティはIDに徹する：状態は外部コンポーネントに置き、柔軟なバージョニングやインデックス設計を可能にする。

- データベースからの学び（Typhonが取り入れた要素）  
  1. コンポーネント単位のMVCC：従来の行単位ではなく、コンポーネントごとに履歴チェーンを持ち、スナップショット分離で読み取りと書き込みを非ブロッキングにする。  
  2. 選択的アクセスのためのインデックス／空間構造：全件スキャンを避けるためにB+TreeやR-Tree、粗いハッシュで空リージョンをO(1)で弾く二層空間インデックスを採用。  
  3. 耐久性と回復：WAL、チェックポイント、fsync選択などをコンポーネント単位で設定可能にし、サーバーの永続状態を守る。  
  4. クエリプランニング：走査か索引かをコスト推定で選択する仕組みを組み込む。

- 実装モデル例（概念）  
  C#の構造体宣言で「1つの宣言がECSとDB両方のスキーマになる」設計を示す：  
  ```csharp
  public struct PlayerComponent {
      public fixed char Name[64]; // String64 相当
      [Index] public int AccountId;
      public float Experience;
  }
  ```

- ストレージモード（使い分け）  
  Versioned（フル履歴、重要データ）、SingleVersion（現在状態＋WAL、頻繁更新だが回復可能）、Transient（メモリ専用、再計算OK）の3種を用途で分離することでオーバーヘッドを最小化。

- ビューと差分更新  
  マテリアライズドビュー風の機構で差分のみを再評価し、毎フレームの「全部走査」を回避する。大量エンティティ中でも変更分だけ処理すれば負荷は激減する。

## 実践ポイント
- データレイアウトは「型ごとの連続領域（SOA）」を優先し、ホットパスのフィールドはまとめて配置する。  
- 頻繁更新・再計算可能な状態は永続化しない（Transient）か、Deferred耐久で運用コストを下げる。  
- 空間クエリが多いなら二層（粗グリッド + R-Tree）を検討し、空リージョンを早期除外する。  
- 重要課金データや進行データはコンポーネント単位で強い耐久・MVCCを与える。  
- 大規模なゲームサーバー設計では「ECSの高速反復」と「DBの安全性」を両立させる思想（コンポーネント＝スキーマ）が有効。

日本のゲーム運営やリアルタイムサービスでは、レイテンシ／運用コスト／耐障害性のバランスが重要。Typhonのような「ゲーム向けに最適化されたデータエンジン」は、この三者を実務的にトレードオフ管理できる設計例として参考になる。
