# From 300KB to 69KB per Token: How LLM Architectures Solve the KV Cache Problem - トークンあたり300KBから69KBへ：LLMアーキテクチャがKVキャッシュ問題をどう解決したか
あなたの会話はGPU上で「重さ」を持つ — メモリ削減で応答が速く、コストも下がる技術の全貌

## 要約
LLMが会話の文脈を保持する「KVキャッシュ」はGPU上に物理的にデータを置くためコストと遅延の原因になる。近年のアーキテクチャ改良（共有キー、潜在圧縮、スライディングウィンドウ等）や代替設計（SSM）は、トークンあたりのメモリを大幅に削減してこの問題に対処している。

## この記事を読むべき理由
GPUコスト、応答速度、会話の一貫性は日本の開発現場でも重要課題です。アーキテクチャ選択や外部メモリの使い方を理解すれば、運用コスト低減とUX改善に直結します。

## 詳細解説
- KVキャッシュとは：入力トークンごとに生成されるキー/バリューをGPU上に保持し、毎回全履歴を再計算することを避ける仕組み（計算を二乗から線形へ改善）。
- メモリ負荷の実例（概算）：初期の設計はトークンあたり約300KiB（例：GPT-2）。以降の改良で128KiB、約69KiBまで下がる事例が報告されている。差は会話長とGPU利用料に直結。
- 進化の方向性：
  - グループ化されたクエリ（GQA）：複数ヘッドでキー/バリューを共有し冗長性を削る。
  - 潜在空間での圧縮（MLAなど）：KVを低次元に圧縮してキャッシュ容量を縮小。
  - スライディングウィンドウ／ローカル重視（Gemma系）：最近の文脈は高精度、古い文脈は粗い保持。
  - State Space Models（SSM）：固定サイズの隠れ状態で増えない記憶を実現する別路線。
- 実ユーザー影響：
  - セッション復帰時の遅延はキャッシュの再構築が原因。多くのプロバイダは短時間でキャッシュを解放する。
  - コンテキストロット（長会話で曖昧化）や、圧縮（コンパクション）による情報損失が実務で問題に。
- コンパクションの二手法：
  - プロンプトによる要約（損失が予測不可）。
  - 学習済みコンパクション（強化学習で要約品質を学ばせる試み。コード等テスト可能な領域で効果が見える）。
- 外部メモリとの棲み分け：長期保持・監査性はファイル、ベクタDB、RAGが有利。KVキャッシュは短期の作業記憶であり、置き換えられるものではない。

## 実践ポイント
- モデル選定：長い対話やコスト重視ならGQAやMLA採用モデル、固定メモリが欲しければSSM系を検討。
- キャッシュ戦略：キャッシュライフタイム、プロバイダの「キャッシュヒット割引」を把握して課金を最適化。
- 長期コンテキストは外部DBで管理：監査や正確性が必要な情報はファイル／ベクタDBで保存し、必要時にRAGで注入する。
- 明示的な要約運用：自動コンパクションに頼らず、重要情報は定期的に人が要約・固定化するルールを作る。
- テストとメトリクス：コンパクションを学習させる場合、明確な報酬（例えばコードの自動テスト）や評価指標を設ける。
- 日本市場への配慮：コスト感、データ保護、監査要件が厳しい分野（金融・医療）では外部メモリとログ保存が特に重要。

短く言えば、KVキャッシュの「物理的な重さ」を減らす工夫は進んでおり、設計選択と周辺インフラ次第でコストと体験は大きく改善できます。
