# My adventure in designing API keys - APIキー設計の冒険

クリックせずにはいられないタイトル: 「APIキー設計でやってしまいがちな落とし穴 — 実運用で検証したベストプラクティス」

## 要約
APIキーの基本から、マルチテナント＋シャーディング環境でのルーティング問題とその解決（SHAKEによる短縮ハッシュ採用）まで、実測ベンチマークとともに整理した実践レポートです。

## この記事を読むべき理由
日本のSaaSやAPIサービス運用者にとって、APIキーの安全性・運用性・検索性能はサービス品質に直結します。特にマルチテナント／シャード構成での設計課題は国内でも重要度が高く、実測に基づく設計判断が参考になります。

## 詳細解説
- APIキーの典型フォーマット：プレフィックス（例：gh_, sk_live）＋ランダム文字列（通常は16進）＋チェックサム。チェックサムでDBを叩く前に入力ミスを弾ける。キーはハッシュ化してDBに保存（生成後1回表示）するのが標準的。
- 問題設定：セッションIDならアカウント→シャードが分かるが、パブリックAPIで受け取る生のAPIキーから「どのシャードにあるか」を高速に特定する必要がある。
- 検討した3案：
  1. APIキーのハッシュをメタシャードにマップする（シンプルで高速だがメタの容量が増える）。
  2. 会社毎にユニークなプレフィックスを割り当てる（メタサイズ削減、だがキーにアカウント情報が露出する・衝突リスク）。
  3. ハッシュを別表現（base62／base70）にエンコードして短縮する（短くなるが、JSでのBigInt変換がボトルネックになり得る）。
- ベンチでの気づき：PostgresのB-Treeは文字列でも高速に検索できるため、単に「長さを短くすれば速くなる」という期待は成り立たない。さらに、JSでの大きな整数操作（BigIntによる基数変換）はソフトウェア実装が重く、全体性能を悪化させる場合がある。
- 最終戦略：SHAKE（SHA-3の可変出力ハッシュ）を使い、必要なバイト数だけ「絞り出す」→ base64urlで短い表現にして先頭10文字を使う方式。これによりインデックスサイズと計算コストを同時に削減しつつ、衝突確率を実用的に低くできる。

補足（衝突確率の概念）: 文字集合サイズを $N$、長さを $L$ とすると組合せ数は $N^L$ で見積れます。適切な $N,L$ を選べば衝突は事実上無視できます。

## 実践ポイント
- APIキーは生成時にしか表示しない。DBにはハッシュを保存する（パスワード扱い）。
- 入力ミス検出のためにチェックサムを付ける（DBアクセス前に検証）。
- マルチテナント＋シャードなら「キー→シャード」マッピング戦略を決める：性能重視ならハッシュマップ、運用性重視ならプレフィックス方式、バランスならSHAKEで短縮した固定長プレフィックス（例：先頭10文字）。
- DBではハッシュ/短縮列にB-Treeインデックスを張る（文字列でも有効）。
- 実装で注意：JSでの大きな基数変換は遅いので避ける。代わりにSHAKEのような可変出力ハッシュ＋base64urlで短縮する手法が効率的。
- ユーザー向けUX：キーは“生成直後にコピー”を促し、管理画面で先頭数文字だけを表示して識別可能にする。
