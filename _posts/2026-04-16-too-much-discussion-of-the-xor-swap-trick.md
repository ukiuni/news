# Too much discussion of the XOR swap trick - XORスワップトリックに関する過剰な議論
XORスワップは「かっこいいけれど実用的ではない」――知られざる理由を端的に解説

## 要約
XORを使った「一時変数なしで入れ替える」トリックは見た目は巧妙だが、コンパイラ最適化や安全性、実装制約の前ではほとんど利点がない。

## この記事を読むべき理由
日常のC/C++コーディングやアセンブリ最適化で「トリックを使うべきか？」と悩む場面がある。日本の現場でも誤用でバグや可読性低下を招きやすいため、判断基準を短く示す。

## 詳細解説
- XORとは  
  排他的論理和（XOR）。ビット単位では $a \oplus a = 0$、$a \oplus 0 = a$ という性質を持つ。これを利用すると以下の代数が成り立つ：$a \oplus b \oplus b = a$。

- XORスワップの本体（Cの例）  
  ```c
  int a = 5, b = 3;
  a ^= b;
  b ^= a;
  a ^= b;
  ```
  これで一時変数を使わずに値が入れ替わる。

- コンパイラ最適化（ローカル変数）  
  最適化付きコンパイラ（例: clang -O2）はローカル変数間のスワップを解析して、XOR命令を使わずに後続命令のレジスタ割付を調整する。つまり、XORトリックは何も生んでいない。

- ポインタ経由のスワップとエイリアス問題  
  ポインタ引数の関数でXORスワップを使うと、同一アドレスを指す引数（alias）がある場合にデータが破壊される。従ってコンパイラは安全のためにXORをそのまま出力する。restrict指定でエイリアスが無いことを保証すれば、コンパイラは通常のロード/ストア版に最適化する。  
  ```c
  void swap_xor(int *a, int *b) { *a ^= *b; *b ^= *a; *a ^= *b; }
  void swap_temp(int *a, int *b) { int t = *a; *a = *b; *b = t; }
  void swap_xor_restrict(int *restrict a, int *restrict b) { *a ^= *b; *b ^= *a; *a ^= *b; }
  ```

- 加算でのスワップ（a = a + b; ...）の問題点  
  整数ではオーバーフローが未定義動作（UB）になり得るため危険。浮動小数点では桁落ちにより値が失われるケースが実際に起こる。

- アセンブリ上の唯一の実用ケース  
  手書きアセンブリで「本当に予備レジスタが一つもない」場合に限り、レジスタのみでの入れ替え手段としてXORスワップは有効。ただしアーキにより命令制約があり（例: Z80のようにAレジスタに限定）、汎用勝ちとは言えない。

## 実践ポイント
- 普段のC/C++ではXORスワップは避ける。可読性が下がり、コンパイラは最適化で同等かそれ以上のコードを生成する。  
- ポインタを渡すAPIでXORを使うとエイリアスで破壊される可能性がある。必要ならrestrictで明示するか、素直な一時変数版を使う。  
- 加算スワップは整数のUBや浮動小数点の精度喪失があるため原則禁止。  
- 手書きアセンブリで本当に「予備レジスタが無い」極限ケースのみ検討。それ以外は単純なmove/storeで十分。

以上を踏まえれば、XORスワップは「面白い雑学」にはなるが、実務コードとしてはほぼ使う必要がない。
