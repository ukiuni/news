# Clean code in the age of coding agents - コーディングエージェント時代のクリーンコード
AIに任せても壊れない「読みやすく小さく分けられた」コードの作り方 — トークンと時間を節約してAIと人の生産性を両立する実践ガイド

## 要約
コーディングエージェント（LLMベースの自動化ツール）を使う上でも、コードの構造（クリーンコード）は重要で、読みやすさ・単純さ・モジュール化・テストしやすさがエージェントの効率とコストに直結する。

## この記事を読むべき理由
日本の開発現場はレガシーや外注・保守の頻度が高く、AIを部分導入しているチームも増えています。AIを使って効率化するなら、何を直せば効果が出るかを知っておくと投資対効果が明確になります。

## 詳細解説
- 価値(value)と構造(structure): Robert Martinの指摘どおり、コードは「動くこと（価値）」と「整理されていること（構造）」の二面性を持ちます。エージェントは動作確認はできても、構造が悪いと余計なファイルを読み込ませる羽目になり、処理コンテキスト（＝トークン量）を浪費します。  
- コンテキスト制約の現実: LLMのコンテキスト長は有限で、読み込む情報が増えるほど性能低下とコスト増につながります。人間と同様、不要な情報を省ける設計が重要です。  
- クリーンコードの要素: 読みやすさ（命名・コメント）、単純さ（過剰抽象の回避）、モジュール化（関心分離）、テストしやすさ（単体テストの容易さ）は、エージェントにも直接効く特性です。  
- エージェントへの指示と学習: LLMはリポジトリのスタイルを把握できるので、構造や期待する設計方針をプロンプトやリポジトリ内ドキュメントで明示すると望む変更を出しやすくなります。ただし成果物のレビューは人間が必須です。

## 実践ポイント
- 小さく切る：1ファイル・1関数の責務を明確に。変更時に読み込むファイルを減らす。  
- 明確な命名とREADME：パッケージ/モジュールごとに短いREADMEを置き、エントリと公開APIを示す。  
- 境界を定義：モジュール間のインターフェースを固定し、変更点を局所化する。  
- テストを充実：ユニットテストを簡単に書ける構造にして、エージェントに「テストを通す変更」を任せやすくする。  
- スタイルとチェック：linters・型チェック・CIを導入し、エージェントが従う「スタイルのルール」を自動化する。  
- エージェントへのプロンプト：実装だけでなく「どのように構造化するか」を明記する（例：変更はこのモジュール内で完結させてください）。  
- 小さなレビュー習慣：エージェントの出力は必ず差分確認してマージ。品質と学習のフィードバックが得られる。  
- コスト意識：大きなリポジトリを丸ごと渡すのではなく、関連ファイルだけを抽出して渡す運用を検討する。  

短期的には「AIがやってくれる」感はありますが、長期的な速度とコスト削減はコードの構造にかかっています。まずは小さなモジュール分割・README整備・テスト強化から始め、エージェントに与える作業単位を小さくすることをおすすめします。
