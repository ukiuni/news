# What's cch? Reverse Engineering Claude Code's Request Signing - Claude Codeの「cch」とは？リクエスト署名のリバースエンジニアリング

Claude Codeの「cch」署名の正体を暴いた調査レポートを、日本のエンジニア向けにわかりやすく再構成しました — ランタイムで密かに行われる署名処理、その設計意図と実務上の影響に注目。

## 要約
Claude Codeは、APIリクエストに隠しメタデータ（cc_version・cc_entrypoint・cch）を注入し、cchをネイティブランタイム側で動的に埋めてリクエスト整合性をチェックしている。署名処理はランタイム内の非公開実装により実行され、動作の検証と影響範囲が明らかになった。

## この記事を読むべき理由
- API連携やCLIを作る日本の開発者が、思わぬ互換性トラブルや課金・機能制御に遭遇する可能性があるため。  
- 独自ランタイムによる「仕様外の振る舞い」（文字列のインプレース変更など）がアプリの信頼性に与える影響を理解できるため。

## 詳細解説
- 観測された仕組み  
  - リクエストには system 配列の先頭に「課金用ヘッダ」を表すテキストブロックが注入され、そこに cc_version / cc_entrypoint / cch が含まれる。cch はリクエストごとに変わる短いハッシュ値で、正しくないと一部機能（例：fast mode）が拒否される。  
  - JavaScript層のコードは cch のプレースホルダ（例：00000）を組み込むだけで、実際の値生成はカスタムビルドされたネイティブの fetch 実装で行われる。つまりハッシュ計算はランタイム内部で完結し、JS 側からは見えない。  
- ランタイムの振る舞いの問題点  
  - 調査では、ネイティブ実装が渡された文字列バッファを書き換えてプレースホルダを置換していることが確認された。これは JavaScript の「文字列は不変」という仕様から逸脱する振る舞いで、参照共有された文字列や Map/Set のキー、内部の rope 構造などに副作用を起こす可能性がある。  
- 署名の範囲と意図  
  - 署名はシリアライズされたリクエストボディ全体を対象としており、メッセージ、ツール定義、メタデータなどの変更はサーバで拒否される設計だった。一方、課金ヘッダ以外の特定の system ブロックはハッシュ計算対象外となるため、完全に不変というわけでもない。  
  - 設計的には暗号的安全性を重視したものではなく、メーターリング／実装同定（“このクライアント実装で組み立てたリクエストか”）を目的にした速いハッシュを採用している。隠蔽（ランタイム内部化）は「難読化」に近い運用判断であり、強力なアクセス制御や暗号的保証を置き換えるものではない。
- リバースエンジニアリングの示唆  
  - 実装や定数はバイナリやランタイムに埋め込まれ更新され得るため、外部クライアント側で互換を保とうとする場合は公式仕様やSDKの利用、ベンダーとの協調が現実的かつ安全な選択である。

## 実践ポイント
- 統合担当者向け
  - 公式SDK／ドキュメントを優先し、ランタイム挙動に依存した非公式の“型落ち”回避は避けること。疑問があればベンダーに問い合わせて正式なガイダンスを得る。  
- 開発者向け
  - JSONのキー順やシリアライズ順序に依存する実装は脆弱になりがち。サーバが署名済みのシリアライズ丸ごとを検証する場合、シリアライズ結果が完全に一致することを前提にする設計は要注意。  
  - 独自ランタイムやカスタムビルド（文字列のインプレース変更など）に依存する動作は、ライブラリ更新や別環境への移植時にバグの温床になる。可能な限り標準に近い実行環境で動作確認を行う。  
- 法的・倫理的注意
  - 隠しヘッダや署名機構を意図的に迂回する行為は規約違反や法的問題を招く可能性がある。互換ツールを作る場合は公開API・OAuthフロー・ライセンスに従い、ベンダーと協調して進めること。
