# Stop using JWTs - JWTの使用をやめよう
驚きの常識崩壊：JWTでログイン管理していませんか？安全でシンプルな正解は「クッキーセッション」です

## 要約
JWT（JSON Web Token）はブラウザのログイン維持（セッション管理）には向かない。設計思想や実運用上の問題で脆弱性や運用コストが増えるため、通常はサーバーサイドのセッション（安全なHTTP-onlyクッキー＋セッションストア）を使うべき、という主張。

## この記事を読むべき理由
日本でもモバイル／SPA／Node.jsが普及し、JWTを使った実装をよく見かけます。見た目は便利でも、誤った使い方はセキュリティ事故や運用負荷につながるため、初級者〜中級者にとって「安全で実践的な認証設計」を学ぶ価値があります。

## 詳細解説
- JWTの本来の想定: 短時間（数分）で使い切る署名付きトークン向け。長期間のセッション保持には設計が合わない。  
- 「ステートレス認証」の誤解: 完全に状態を持たない安全なセッションは現実的に困難。リフレッシュ・失効・ログアウト・ローテーション等はサーバー側の状態管理（データストア）を必要とする。  
- セキュリティ問題点: JWTにユーザ状態や有効期限・権限を詰め込むと、改竄・再利用・失効管理が複雑に。仕様の余地（誤実装の余地）やベストプラクティスの不足も指摘される。  
- ブラウザ側保存の危険: localStorage/sessionStorageに認証情報（JWT等）を置くとXSSで盗まれるリスクが高く、推奨されない。  
- 実際の大手のやり方: Googleなど主要サービスはブラウザのユーザーセッションに安全なクッキーセッションを使っている（署名・暗号化されたクッキー＋サーバー側管理）。  
- JWTの適切な用途: 短期のワンタイム認可トークンやサーバ間のSSOトークンなど、限定的・短命なユースケースなら有用。より安全な代替としてPASETOなどが提案されている。  
- スケーリング: セッションを共有DB（Postgres等）やRedisで管理すればサーバー群での共有は解決可能。大規模向けでもセッションストアは一般的な選択肢。

## 実践ポイント
- ブラウザ認証はまず「セキュアでHTTP-onlyなクッキー＋サーバーサイドセッション」を検討する。  
- cookie属性は必ず Secure, HttpOnly, SameSite を設定する。ドメイン/パスを適切に絞る。  
- localStorageにトークンを置かない。XSS対策（Content Security Policy、入力サニタイズ）も必須。  
- JWTは「短期・使い捨てトークン」「SSOの一時搬送」など限定的に使う。長期セッションには使わない。  
- 既存フレームワークを活用：Expressなら express-session＋適切なストア（connect-session-knex, Redis等）を使う。  
- 失効・ローテーション設計を入れる（ログアウト時の即時失効、長期トークンのローテーション）。  
- 代替検討：署名トークンが必要ならPASETOを検討する。  

短い結論：見た目の手軽さでJWTをセッションに流用しないこと。まずは安全なクッキーセッションを標準にし、必要に応じて限定的にトークンを使う設計を。
