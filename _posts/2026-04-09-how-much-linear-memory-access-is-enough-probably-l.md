# How Much Linear Memory Access Is Enough? (probably less than 128 kB) - 線形メモリアクセスはどれくらい必要か？（多くは128 kB未満で足りる可能性）

魅力的な日本語タイトル：小さなチャンクで速く回せる？メモリの「連続性」はどこまで必要かを実験で検証

## 要約
元記事は「線形（連続）メモリブロックのサイズが性能に与える影響」を実測で調べ、ほとんどのワークロードで $1\ \mathrm{MB}$、多くは $128\ \mathrm{kB}$ またはそれ以下で十分になると結論づけています。

## この記事を読むべき理由
メモリ配置・アクセスは高速化の基本。日本でゲーム、3D、データ処理、組み込みなどを扱うエンジニアにとって、チャンクサイズ設計の実務的ガイドラインになるため「無駄に大きな連続領域」を保持せずに済む可能性があります。

## 詳細解説
- 目的：データを「ブロック（チャンク）」単位で処理する際、各ブロックをどれだけ連続させればブロック間のジャンプが性能にほとんど影響しないかを計測。  
- 実験概要：ブロックサイズを $32\ \mathrm{B}$ 〜 $2\ \mathrm{MB}$、ワーキングセットは $1\ \mathrm{MB}$ 〜 $64\ \mathrm{MB}$、ランダム配置＋キャッシュ“clobber”（256 MB を掃き出す処理）で「冷えた」条件を作り、中央値で評価。  
- カーネル（代表例）：
  - scalar_stats：軽量なスカラー集計で大きなブロックで約 $7\ \mathrm{GB/s}$（約 $3$ サイクル/float、 ~$0.75$ サイクル/byte）。
  - simd_sum：AVX2/NEON を使った SIMD 集計で $50+$ GB/s（約 $0.1$ サイクル/byte）—最も帯域要求が高いケース。
  - heavy_sin：重い算術（sin ループ）で約 $450\ \mathrm{MB/s}$（約 $40$ サイクル/float、~$10$ サイクル/byte）—計算バウンド寄り。
- 主要な観察：
  - 一般に、ブロックサイズを増やしても利得は頭打ちになる（奏功するしきい値あり）。
  - simd_sum のような帯域効率が非常に高い処理では $1\ \mathrm{MB}$ 程度のブロックを要することがある。
  - 多くの実務的処理では $128\ \mathrm{kB}$ で十分。計算コストが高ければ $4\ \mathrm{kB}$〜$16\ \mathrm{kB}$ でも済む場合がある。
  - 「繰り返しアクセス（温まった状態）」だと小さいワーキングセットはさらに小さいブロックでピークに到達する（TLB/キャッシュ再利用の影響）。

## 実践ポイント
- 初期方針：汎用的には $128\ \mathrm{kB}$ を目安に設計。極端に高効率な SIMD 集計が主なら $1\ \mathrm{MB}$ を検討。  
- 計算負荷が高い処理（>~$10$ サイクル/byte）なら $4$〜$16\ \mathrm{kB}$ でも問題ない。  
- ブロック単位での割当てや固定の per-block コスト（割当・初期化など）があるなら、実装コストを含めて再測定が必要。  
- 実際の環境で必ずベンチを回す（TLB、キャッシュ構成、CPU 世代で結果は変わる）。元記事のベンチコードは公開されているので自分のマシンで試すと良い。  
- API 設計上は可能なら contiguous を受け取れる形（例：span<T const>）を維持しつつ、内部は小チャンク化しても問題ないと分かった点を活かす。

短くまとめると、「連続メモリは重要だが、“大きければ大きいほど良い” ではない。運用上は $128\ \mathrm{kB}$ 程度を出発点に、ワークロードに応じて上下調整してベンチを回すのが現実的」です。
