# Dennis Ritchie on & | vs. == - 初期Cにおける & と | の二重の役割
クリックせずにはいられないタイトル: 「if (a==b & c==d) が起こした設計判断—Ritchieが語る短絡評価と互換性のジレンマ」

## 要約
初期のCは文脈に応じて `&` と `|` を論理（短絡ではない）あるいはビット演算として使い分けていたが、後に `&&` と `||` が導入され、ビット演算と論理評価を分離した。設計者は既存コードとの互換性を優先して演算子の優先順位を変えなかった。

## この記事を読むべき理由
演算子の動作と優先順位はバグ原因になりやすく、日本の組込み／レガシーC開発や教育現場でも実務レベルで影響するため、歴史的背景と設計判断を知っておくと読み書き・保守に役立ちます。

## 詳細解説
- 背景：BやBCPLの影響で、初期Cは「真値文脈」（if や while の条件式など）では `&` と `|` を論理演算（真偽の連結）として扱い、通常の式ではビット演算として扱っていた。  
- 問題点：この二重解釈は理解しにくく、コード例として `if (a==b & c==d)` のような書き方が生じると、読み手が意図を誤解しやすい（`&` がビット演算なのか論理結合なのか）。  
- 解決策：Alan Snyder の勧めで `&&` と `||` が追加され、短絡評価（左辺が偽なら右辺を評価しない）という振る舞いとビット演算を明確に分離した。  
- 互換性トレードオフ：`&` の優先順位を `==` より高く変えれば混乱は減ったかもしれないが、既存数十万バイトのソースに与える影響を避けるため、Ritchie は優先順位を変更しなかった（分離のみ実施）。結果として現在のCの優先順位体系と演算子セットが定着した。

簡単な例（意図と現実のズレ）:
```c
c
if (a == b & c == d)  /* 読み手は (a==b) && (c==d) を期待することが多い */
    ...
```

## 実践ポイント
- 論理結合には常に `&&` / `||` を使う（`&` / `|` はビット演算と明確に使い分ける）。  
- 書き手・レビュー時は括弧で意図を明示する： `(a==b) && (c==d)`。  
- コンパイラ警告を有効化する（例: -Wall）／静的解析ツールで `if` 条件の怪しいパターンを検出する。  
- レガシーコードでは `grep` によるパターン検索で `== .* [&|]` のような危険箇所を洗い出し、テストで挙動を確認してから修正する。

歴史は設計上の妥協を教えてくれます。今日のコード品質はこうした判断を踏まえた小さな習慣から築かれます。
