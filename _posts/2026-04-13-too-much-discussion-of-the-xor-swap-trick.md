# Too much Discussion of the XOR swap trick - XORスワップ・トリックについて議論しすぎな件
「一時変数を使わず入れ替え」は本当に得か？コンパイラとアーキで検証するXORスワップの現実

## 要約
XORスワップはビット演算だけで変数を交換するトリックだが、ほとんどの実用シーンではコンパイラが最適化するか、逆に遅く・危険になる。真に有用なのはごく限られたアセンブリ状況のみ。

## この記事を読むべき理由
言語レベルで見聞きする「かっこいい最適化」が実際のコードや性能にどう影響するかを理解できる。組み込み・レガシーCPUや面接問題対策としても役立つ。

## 詳細解説
XORの基本性質：
- ビット単位の排他的論理和: $a \oplus a = 0$, $a \oplus 0 = a$。したがって $a \oplus b \oplus b = a$。
- これを利用して一時変数なしで交換できる。

典型的なCの実装例：
```c
// C
a ^= b;
b ^= a;
a ^= b;
```
一時変数を使う普通の交換：
```c
// C
int tmp = a;
a = b;
b = tmp;
```

コンパイラ最適化（例: clang -O2, x86-64）
- ローカル変数を関数内で入れ替える場合、コンパイラは「どの値を最終的に使うか」を追跡してスワップを丸ごと消し、結果だけ正しく出す（XOR命令は出力されない）。
- ポインタ経由のswap関数では、XOR版はメモリ読み書き・再読み込みを多く行い命令数が増える（例: 6命令 vs 一時変数版の4命令）。つまり逆効果。

エイリアス問題（同一アドレスへのポインタ）
- swap_xor(&x,&x) は最初の *a ^= *b が $x \oplus x = 0$ を書き込みデータを壊す。したがってコンパイラはXOR版を単純なロード/ストアに置き換えられない。
- Cのrestrictを使えば「異なるアドレスである」と保証でき、コンパイラはXORを簡単なロード/ストアに最適化できる。

加算によるスワップ（a=a+b; b=a-b; a=a-b;）
- 整数版は符号付きオーバーフローで未定義動作（UB）となる可能性があり危険。実装上は現実的に正しく動くことが多くとも、言語仕様上は誤り。
- 浮動小数点では精度喪失で値が消えるケースがある（例: 1.0 と 1e16 を交換すると 1.0 が捨てられる）。

アセンブリでの唯一の利点
- レジスタに収まっていて「予備レジスタが全く使えない」場合、XORでレジスタ間を追加メモリなしに3命令で入れ替えられるため有利になり得る（レジスタ逼迫した最適化されたループ等）。
- ただし多くのアーキ（例: Z80 のように XOR が A レジスタ限定）や実際のx86流儀では適用が難しいか無意味。

結論（技術的要点）
- 高レベルコードでは使わない。可読性低下・誤りリスク・性能悪化の方が目立つ。
- 低レベルでレジスタが極端に不足する特殊ケースのみ検討する価値あり。

## 実践ポイント
- 普通は一時変数版（tmpを使う）を使う。読みやすく安全でコンパイラも最適化する。
- ポインタを使う関数でXORを使うとエイリアスでデータ破壊する可能性がある。どうしてもならrestrictで明示するか避ける。
- 加算スワップは符号付き整数でUB、浮動小数点で精度喪失があるので使わない。
- 組み込み/アセンブリで本当にレジスタが足りない場面だけXORスワップを検討し、アーキ制約（命令の書き換え可否）を確認する。
