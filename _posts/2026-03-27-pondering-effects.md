# Pondering Effects - エフェクトを熟考する
副作用（エフェクト）を「ちゃんと考える」だけで、バグと運用コストが激減する理由

## 要約
エフェクト（外部とのやり取りや状態変更）を設計段階で明示的に扱うと、可観測性・テスト容易性・信頼性が向上する。フロントエンドのuseEffectからマイクロサービスの副作用まで、共通の考え方がある。

## この記事を読むべき理由
日本でもReact/Vueやクラウドマイクロサービスが一般化しており、エフェクト管理の失敗は顧客体験や運用コストに直結します。初級者でも実践できる対策を知ることで、現場で即効性のある改善ができます。

## 詳細解説
- 用語整理：純粋関数は入力→出力のみ。エフェクトはログ出力、DB書き込み、ネットワーク、タイマー、DOM操作など外部副作用を伴う処理。
- なぜ問題になるか：副作用が分散・非同期だと再現性が落ち、テストが困難に。依存関係の見落としで不整合やメモリリークが発生する。
- フロントエンドの代表例：ReactのuseEffect。依存配列の扱いを誤ると意図しない再実行やクリーンアップ不足でバグに。下記は安全なクリーンアップの例。

```javascript
// javascript
import { useEffect } from 'react';

function MyComponent({ id }) {
  useEffect(() => {
    let mounted = true;
    const controller = new AbortController();

    fetch(`/api/item/${id}`, { signal: controller.signal })
      .then(res => res.json())
      .then(data => { if (mounted) { /* state更新 */ } });

    return () => {
      mounted = false;
      controller.abort(); // クリーンアップで副作用を止める
    };
  }, [id]);
}
```

- サーバー/分散システムの観点：外部APIの遅延や部分失敗への対処（リトライ戦略、指数バックオフ、サーキットブレーカー、冪等化）が必須。イベント駆動設計では"副作用"をイベントハンドラに隔離するとロジックがテストしやすくなる。
- モデル化のアプローチ：副作用を明示的に扱う（Effect Handlers / IOモナド /コマンドとイベントの分離）ことで、ビジネスロジックを純粋関数に保てる。
- 観測性：ログ・メトリクス・トレースで副作用の経路を可視化。欠損トレースは障害対応を遅らせる。

## 実践ポイント
- まず「どこに副作用があるか」を一覧化する（DB、API、ストレージ、タイマー、UI操作）。
- 副作用を呼ぶ場所を薄く保ち、ビジネスロジックは純粋関数に分離する。
- フロントはuseEffectの依存配列とクリーンアップを徹底する。非同期中止にはAbortControllerなどを使う。
- サーバーはリトライ、バックオフ、冪等設計、サーキットブレーカーを組み合わせる。
- テスト：副作用をモック・差し替え可能にしてユニットテストを容易にする。統合テストで実環境に近い検証を行う。
- 観測性を標準化（ログフォーマット、トレースID、メトリクス）し、障害時に因果関係を追えるようにする。
- 日本企業向けTip：SLAやカスタマーサポート負荷を下げるため、特に外部API周りとリトライ設計に投資すると効果が大きい。

短時間で始めるなら「副作用の一覧化→重要度の高い箇所に監視/クリーンアップを入れる」から。まずは一箇所のエフェクトを明示的に扱う習慣を付けましょう。
