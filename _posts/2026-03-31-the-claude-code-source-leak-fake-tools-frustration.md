# The Claude Code Source Leak: fake tools, frustration regexes, undercover mode - Claude Codeのソース流出：偽ツール、感情検出（正規表現）、隠れモード
魅力タイトル：Anthropicの「Claude Code」流出で判明した裏設計──偽装ツール、AIが自分を隠す仕組み、未発表エージェントまで

## 要約
Anthropicがnpmパッケージに誤ってソースマップを含めたことで、Claude Codeの内部設計が公開された。偽ツール注入、AIが自身を隠す「Undercover」モード、ネイティブレイヤでのクライアント証明、未発表の自律エージェント“KAIROS”など、競争戦略と技術的トリックが明らかになった。

## この記事を読むべき理由
この流出は単なるコードリークではなく、API保護（技術＋法務）、プロダクトのロードマップ、そして実運用上の落とし穴（ビルド設定やセキュリティ）が透けて見える事例。日本のプロダクト／SRE／セキュリティ担当が学ぶべき教訓が豊富にある。

## 詳細解説
- Anti‑distillation（偽情報注入）  
  - クライアント側フラグでAPIにanti_distillation指示を送り、サーバが誘導的な「偽ツール定義」をシステムプロンプトに混ぜる。盗用目的でAPI通信を録って学習する攻撃者のデータを汚染する狙い。だがリクエストを改変するMITMや第三者プロバイダ経由では回避可能で、実際はフラグやビルド設定に依存する。
- Connector‑text要約（サーバ側要約＋署名）  
  - ツール呼び出し間のテキストを要約して署名で返す方式で、トラフィックを録るだけだと要約しか得られない仕組みがあった（社内向け限定）。
- Undercoverモード（AIが“AI”を隠す）  
  - 外部利用時に内部コードネームや「Claude Code」という言及を絶対に出さないようにする機能。ONは強制できるがOFFに戻せない一方通行の実装で、OSSでのAI著作表示を曖昧にする懸念がある。
- フラストレーション検出に正規表現を使用  
  - ユーザの罵倒や不満を検出するのにシンプルな正規表現を使っている。LLMで判定するより高速廉価な選択だが皮肉な話でもある。
- ネイティブクライアント認証（JS下のZig実装）  
  - HTTPヘッダにプレースホルダを入れ、Bunのネイティブ実装（Zig）で実行時にハッシュを書き換えてサーバが検証する仕組み。バイナリレベルでの証明を行うが、ビルドフラグや環境変数で無効化できたり、別実行環境で動かすとプレースホルダのまま送られるなど抜け穴もある。
- 無駄なAPIコール250K/日とシンプルな修正  
  - 連続失敗が多発してAPIコールが大量に浪費されていた。上限を「3回」にするだけで改善された事例がソースコメントに残る（データ駆動の小さな修正の効果）。
- KAIROS（未発表の常駐エージェント）  
  - 毎夜の記憶蒸留、日次ログ追記、GitHubフック、バックグラウンドワーカー、5分間隔のリフレッシュなど、常時稼働する自律エージェントの足跡がある。機能フラグで封印されているが、プロダクト戦略上の大きなリーク。
- その他の注目点  
  - April Fools的な“バディ”機能の痕跡、端末描画の最適化（ストリーミング時の文字幅計算削減）、シェルコマンド向け多層セキュリティチェック、プロンプトキャッシュ設計（トークン課金が設計を左右する）など実運用志向の実装が多い。逆に巨大な単一関数やAxios依存のリスクも見える。
- 流出原因の可能性：Bunのソースマップ挙動  
  - Bunの既知の問題で本番ビルドにソースマップが出る報告があり、これが直接のトリガになった疑いがある。

## 実践ポイント
- ビルド/公開設定でソースマップやデバッグ情報が混入していないか必ず確認する（CIで自動チェックを入れる）。  
- クライアント証明（attestation）を導入する場合、失効・無効化経路やフォールバックを設計しておく。  
- コストが直接影響する箇所（プロンプトキャッシュや自動圧縮）は小さな閾値変更で大幅改善することがある。ログで「何を何回失敗したか」を可視化する。  
- OSSやコントリビューション方針では「AIで生成された変更の表示」を明確化する。Undercover的な自動隠蔽は信用問題を招く。  
- 依存パッケージ（例：Axios）の供給チェーンリスクを常に監視し、脆弱・悪意あるバージョン混入に備える。  
- 未発表の常駐機能（自律エージェント）が出てきた場合のプライバシー/運用影響を評価しておく。

著者注：今回の流出は「コード」以上に「設定とフラグ」が戦略情報であることを示している。日本のプロダクト運用でも、技術的対策とルール設計の両輪で対策することが重要だ。
