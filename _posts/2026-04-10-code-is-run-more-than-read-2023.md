# Code is run more than read (2023) - コードは「読む」より「動かす」方が重要だ
ユーザーと運用を最優先にする開発観が、プロダクトの成功と現場のストレスを左右する

## 要約
コードは「読む」より「書く」や「読む」より「動かす」側面が重要で、特に本番環境での運用コストやユーザー体験を起点に設計すべきだという主張。

## この記事を読むべき理由
日本のプロダクト開発でも、仕様通りに動くかだけでなく「運用できるか」「顧客に価値を届けるか」が利益や現場の負荷に直結します。早めに実運用を意識する発想は、開発効率と品質を同時に上げます。

## 詳細解説
- 古典的な格言「コードは読む回数が書く回数を超える」を出発点に、著者は優先順位のモデルを提案。代表例は user > maintainer > author → 最終的には user > ops > dev の重要度。
- 「run」は単なる実行ではなく、デプロイ、監視、アップグレード、障害対応、廃止まで含む運用の全工程を指す。運用コストは初期開発コストを長期的に上回ることが多い。
- よくあるアンチパターン：作った人しか直せないコード（author > maintainer）、ユーザー無視の過設計（dev > user）、運用を考慮しない「Works on my machine」（dev > ops）など。
- ビジネス面の要請（予算・マーケ・期限）がユーザー優先とぶつかる場面もあるため、実務では biz > user > ops > dev のような力学が働く。重要なのは「ビジネスを無視して良いわけではないが、ビジネスが常に最優先であるべきでもない」点。
- 著者はKISS（Keep It Simple, Stupid）を運用観点で再定義し、移動部分を減らし故障モードを理解することの重要性を強調する。

## 実践ポイント
- なるべく早くプロトタイプをユーザーに触れさせ、実際の運用で得たフィードバックを素早く反映する。  
- 運用を設計段階から含める：監視・ロギング・デプロイ手順・ロールバックを最初から決める。  
- 技術選定は「解決すべき問題」と運用コストで評価する（過剰な最先端採用は要注意）。  
- 小さくシンプルに作り、失敗時の影響範囲を限定する（マイクロ最適化より障害境界の設計）。  
- ビジネス目標とユーザー価値を両方見て優先順位を判断する。社内ツールやB2Bでは特に運用負荷が利益に直結する点を重視する。
