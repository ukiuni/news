# HTTP desync in Discord's media proxy: Spying on a whole platform - Discordのメディアプロキシで見つかったHTTPデシンク：プラットフォーム全体を覗く脆弱性
Discordの画像が“横取り”される仕組み──HTTPデシンクがもたらした恐るべき現実

## 要約
Discordのメディアプロキシで見つかった「HTTPデシンク（リクエスト/ボディ同期ずれ）」により、接続プーリングと不正な入力が組み合わさることで、他ユーザーのメディア要求を横取りして閲覧できる状態が発生していた。報告者は脆弱性を報告し、解決済み・報奨金が支払われている。

## この記事を読むべき理由
HTTPプロトコルの細かな仕様ミスや接続管理の不備が、巨大サービスのプライバシーを一瞬で侵害し得ることを示す事例は、日本のサービス設計者や運用者にとって他人事ではありません。特にクラウドストレージ連携やリバースプロキシ、接続プールを使う設計は国内でも広く用いられています。

## 詳細解説
- 問題の本質  
  「HTTPデシンク」は、プロキシやバックエンド間で送受信されるHTTPメッセージの境界がずれることを指します。たとえば不正な制御文字や不正な長さ指定（Content-Length）などで一つの接続上に本来想定していない追加リクエストやボディが混入すると、次に同じ接続を借りた別の要求が「ボディの続き」として解釈される可能性があります。

- 発生要因（高レベル）  
  1) フロントエンドがユーザー入力をほぼそのままプロキシ先のリクエストに差し込んだ。  
  2) 改行や制御文字が上流のHTTPメッセージとして伝搬できてしまった。  
  3) バックエンドのGCP接続が接続プールで再利用され、前リクエストの不整合が次の借用者に影響した。  
  これらが組み合わさり、攻撃者が意図的に「未送信のボディ領域」を確保しておき、次に流れてきた正当なリクエストをその不足分で上書き・記録する、という横取りが可能になりました。

- 影響範囲  
  実際に確認されたのは、メディア配信のリクエスト（画像等）のパス情報が攻撃者側のストレージに書き込まれ、世界中の閲覧トラフィックがリアルタイムで露出する事態。公開サーバー／プライベートDM問わず、メディア閲覧のパスが対象になり得ます。

- 補足（技術的注意）  
  この種の挙動はライブラリやプラットフォームの実装依存で生じるため、単に「入力を消毒すれば良い」という簡単な話ではありません。接続の取り扱い（プーリング、フラッシュ、ストリームの境界処理）、HTTPパーサの堅牢性、プロキシの正規化処理が全て関与します。

## 実践ポイント
- 受け入れ側（プロキシ/バックエンド）での入力検証  
  - 要求パスやヘッダに改行・復帰（\r,\n）や制御文字が含まれていないか厳格に検査して拒否する。  
  - パスの正規化（URLデコード→検証→再エンコード）を行い、生データをそのままプロキシ先に流さない。  
  - Content-LengthやTransfer-Encodingの不整合を検出して接続を切る。

- 接続プールとストリーム管理の見直し  
  - 接続を再利用する際は必ず前回のレスポンス/リクエストが完全に消費されていることを確認する。  
  - 未消化データや部分的なボディが残る可能性がある実装では接続の再利用を無効にするか、専用対策を入れる。

- ログと検知  
  - 異常なPUTや予期しないアップロード、短時間での多数の部分書き込みをモニタしてアラートを出す。  
  - 外部ストレージでの書き込みコンテンツに対する検査（予期しないHTTPメソッドやサイズのズレ）を行う。

- 開発側のベストプラクティス  
  - 信頼できるHTTPライブラリを使い、パーサやフレームワークの脆弱性に注意する。  
  - サードパーティと連携する際は最小権限・短い署名付きURL・限定的なHTTPメソッドを使う。  
  - バグバウンティやインシデント対応プロセスを整備して速やかに報告・修正できる体制を持つ。

安全な入力検査の簡易例（説明用、実稼働前に要レビュー）:
```python
# python
def is_safe_path(path: str) -> bool:
    # 制御文字や改行を拒否（簡易チェック）
    return all(0x20 <= ord(ch) <= 0x7e for ch in path)
```
